# Retro: the Fases 1-3 build

Scope: the work that actually built TTX-247 — 2026-09-18 09:37 UTC through
2026-09-25 08:20 UTC, across the Claude Code sessions logged under this
project's directory in that window. Written using the `/retro` skill,
grounded in a Python pass over the raw session transcripts (not a
skimmed re-read) plus `git log`/`gh pr list`/`gh issue list` at write time.

**20 session files exist in that window; 18 are in scope.** Two were
excluded after checking their actual first message, not just their
timestamp: one (2026-09-27, tools `game-development`/`grill-me`) is
entirely about animating assets for the unrelated `8bit` project, and one
(2026-09-28, "I am trying to install mySQL community server") is an
unrelated troubleshooting question. Both were logged under this
project's Claude directory anyway — see *Process gaps* below; this is
itself a finding, not just a filtering footnote.

**Grounded totals (18 in-scope sessions):** 156 user turns, ~1,291 tool
calls, 57 tool-result errors (see below — mostly one early session, not
spread evenly). 175 commits landed on `main` in this window, across 35
merged PRs and **zero** PRs closed without merging. 92 issues were
created; exactly one (`#60`, TD.8) was closed `NOT_PLANNED` — open one day,
superseded by TD.10 per `Backlog.md`'s own note.

## Critical retrospective

**Agent behavior:**
- The early tool-error spike (20/130 in the first session) was a real
  cost, but a one-time one — the pattern didn't repeat later in the
  build, so no standing fix is needed beyond what already happened
  (the environment got sorted once, early).
- No evidence in the transcripts of a drafted-then-discarded deliverable
  anywhere in Fases 1-3, unlike the 2026-09-28 Fase 4 session. The
  difference is procedural, not luck: every phase kickoff ran `grill-me`
  to completion *before* any implementation started, so there was never
  a half-finished draft sitting on top of an unconfirmed decision.

**Process/collaboration gaps:**
- Two sessions' worth of unrelated work (a different project's game
  assets, a MySQL install question) landed in this project's Claude
  directory because the working directory wasn't switched first. Low
  cost here (it doesn't pollute the codebase), but it does mean anyone
  auditing "this project's sessions" has to filter by content, not just
  by folder — which is exactly what this retro had to do.
- The requirements shift that produced TD.10-TD.12 (typed commands →
  numbered menu) is legitimate client-driven change, but it's also the
  build's only real instance of "build it, then rebuild it" — worth
  naming even though the root cause sits outside the AI-assisted process
  itself, because it's still real engineering cost that a pre-build
  clarifying question (how should the driver select an option — typed or
  numbered?) might have caught before Fase 1 shipped its first CLI.

**What went well — keep doing this:**
- Grilling before coding, every phase, without exception, is the
  single clearest pattern in the whole build and the main reason Fases
  1-3 produced zero abandoned PRs and only one superseded issue across
  92 opened.
- Issues that turn out superseded get closed with a reason on the
  record (`NOT_PLANNED`, with the superseding task named in
  `Backlog.md`) within a day, not left open or silently abandoned.
- Decisions docs written *as* decisions were made (`decisions-fase*.md`
  carry dates matching the commits) rather than reconstructed after the
  fact — this is exactly what made this retro possible to ground instead
  of guess at.

## Conclusions

- Grilling to completion before any code is written is the build's
  strongest habit, and it is precisely the habit the 2026-09-28 session
  broke — that comparison is the most useful single finding across both
  retros so far.
- Early tool-error spikes from environment setup are a one-time cost,
  not a recurring one, once actually checked against the transcript
  instead of assumed from a raw error count.
- A superseded issue costs little if it's caught within a day and closed
  with a reason — the failure mode to watch for is a superseded issue
  left open, which didn't happen here.
- Client-driven UI revisions after a phase has already shipped are real
  rework; a clarifying question at kickoff (as later grilling sessions
  consistently did) is cheaper than a revision after the fact.
- Session directory hygiene (switching `cwd` before unrelated work) is
  the only clean "housekeeping" finding this pass turned up — small, but
  worth a one-line guideline.

## Guidelines

1. Keep running `grill-me` to completion before starting implementation
   on any new phase or story — this build's record (zero abandoned PRs,
   one superseded issue caught in a day) is the direct result of that
   habit, not incidental.
2. When a UI/UX shape (typed commands vs. numbered menu, in this build)
   is genuinely ambiguous from the brief, ask about it explicitly during
   the phase's grilling session, before the first implementation —
   TD.10-TD.12 shows what it costs to find out after.
3. Switch the working directory before starting work on a different
   project, even for a short question — two sessions in this window
   were about unrelated projects but got logged here anyway.
4. When a task turns out superseded mid-build, close it with a reason
   the same day, the way TD.8 was — don't let a stale issue linger.
